# 4. Project files

**Goal:** Know which files you edit, which kive generates, and where the `hello` job lives in the tree.

**Prerequisites:** [Chapter 3 — The model](03-the-model.md).

## Bucket layout

```text
./                          # bucket root — kive finds this via kive.conf / data/kive.db
├── kive.conf              # SSH user, key, optional settings
├── data/kive.db           # catalog (output of build — do not edit by hand)
├── workspace/              # source of truth you edit (git)
│   ├── workers.conf
│   └── jobs/hello/
│       ├── job.conf
│       └── Makefile
├── secrets/                # SSH private key, CA, KV encryption key
└── logs/                   # kive command logs
```

Two directories are not part of `kive init` and appear only when something needs them: **`tmp/`** is scratch that commands create and remove again (deploy staging lives there while a command runs), and **`templates/`** exists only if you add job templates for `kive job create --job-template`.

You can run **`kive`** from a subdirectory of the bucket, or set **`BUCKET_ROOT`** to the bucket path. See [configuration](../reference/configuration.md).

**Rule:** if it is under **`workspace/`**, you change it and run **`kive build`**. Worker runtime dirs (`data/`, `logs/` on the worker) are created by your Makefile, not checked into workspace.

Hand-edit these files after `kive init`.

## What you edit vs what kive owns

| Path | You edit? | Purpose |
|------|-----------|---------|
| `workspace/` | **Yes** (git) | Workers, jobs, optional `disabled.conf` |
| `kive.conf` | **Yes** | SSH settings |
| `workspace/bucket.conf` | **Yes** | Port pool, cert TTL / renewal, iptables, bucket vars |
| `workspace/bucket.jobs.conf` | **Yes** | Per-job CPU/memory reservations (empty until you fill it in) |
| `secrets/` | **Carefully** | Keys — usually not in git |
| `data/kive.db` | **No** | SQLite catalog from **build** |
| `logs/` | **No** | Command logs |
| `tmp/` | **No** | Scratch staging; created per command and removed after |
| `templates/` | **Yes**, if you use it | Optional job templates; not created by `init` |

## `kive.conf` essentials

```text
ssh {
  user("agent");
  key("worker.key");
};
ssh {
  use_sudo(true);
};
```

Full options: [Reference: configuration](../reference/configuration.md).

## Build vs deploy (two phases)

```text
workspace ──kive build──► kive.db on CLI host ──kive deploy──► worker /opt/kive/...
```

- **Build** validates and records intent — no SSH to workers (except hook scripts on the CLI host).
- **Deploy** reads the catalog and pushes to workers.

This lets you catch placement and resource errors before touching production hosts.

## Optional workspace files (later)

| File | Purpose |
|------|---------|
| `workspace/disabled.conf` | Drain nodes or jobs without deleting definitions |
| `workspace/jobs/<job>/vars.conf` | Stable job app config |
| `workspace/jobs/<job>/_prometheus/` | Optional scrape, alerts, runbooks, dashboards |

You do not need these for the `hello` tutorial. Fill in **`bucket.jobs.conf`** when jobs need explicit CPU/memory reservations.

## What you learned

- **`workspace/`** is what you commit; **`kive.db`** is generated by build
- **`kive.conf`** and **`secrets/`** configure SSH from the CLI host
- **Build** is local; **deploy** reaches workers
